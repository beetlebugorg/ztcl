Tcl, compiled. Up to 28 times faster than tclsh.

On a 10-million-pass integer loop, ztcl with JIT tier 2 runs in 15 ms. tclsh 8.6.16 uses 413 ms. With the JIT off, the bytecode interpreter is 1.6 to 3.5 times as fast as tclsh on the benchmark scripts.

Speed and the JIT

A bytecode VM, and a JIT compiler for hot loops.

The interpreter compiles each script to bytecode. On x86-64 Linux, the optional JIT compiles hot procs to machine code, and tier 2 keeps integer and double loop variables in registers. tclsh 8.6 and 9 have no JIT. The JIT is experimental and off by default.

Larger programs

Three programs of kostya/benchmarks: the brainfuck interpreter bf.tcl, its TclOO version bf_oo.tcl, and base64. With small.b, each output of ztcl equals the output of tclsh 8.6.16.

Exact, deterministic limits

Limits that Tcl does not have.

The interp limit command of Tcl counts commands and time, and it has no memory limit. ztcl counts steps exactly and puts a hard cap on memory. Your program sets both before it runs a script that it did not write.

An exact step limit

Each command and each loop pass uses steps. At the limit, the script stops with an error that catch and try cannot catch.

  • The limit holds in JIT machine code too.
  • No clock is involved, so a slow machine gets the same count.

A hard memory cap

The heap of an interpreter and its children never goes above twice the memory limit. One command can go over the limit by at most the limit itself.

  • A large request stops before the allocation.
  • Nesting limits protect the native stack.

The same stop on each run

A script stops at the same step on each machine and in each JIT tier. A JIT run gives the same step counts as the interpreter on the whole Tcl test suite.

  • With no capability on, output depends only on the script, the seed, and the inputs.
  • The collector can move the point of the memory error. --gc off makes it exact.

Host access is a capability

The safe interps of Tcl also remove files, sockets, and exec. In ztcl, the default interpreter starts with no host command, and your program turns on each capability with its own policy.

  • file and channels stay inside one root folder.
  • socket follows a network policy: loopback, an allowlist, or any.
  • A child interp never has more capabilities than its parent.
  • exec is not sandboxed. A process from exec runs outside the root folder and outside each limit, with the full power of the user.

Embedding in Zig

One static binary of 2.5 MB, with the JIT.

ztcl is a Zig package with no dependency outside the Zig standard library. zig fetch adds it, and no C toolchain is necessary. On the benchmark machine, the stripped ztcl binary is 2.5 MB. The libtcl8.6.so of the Linux distribution is 9.2 MB, before its script library.

  • Cross-compiles with zig build -Dtarget=…. From x86-64 Linux, it builds for arm64 Linux, arm64 macOS, x86-64 Windows, and 64-bit RISC-V Linux. CI tests on Linux, macOS, and Windows.
  • register(name, fn) adds a native command.
  • output is the callback of puts.
  • enableJit(.{}) turns on the JIT where the build has one.

WebAssembly

The same interpreter in the browser.

zig build wasm builds a module of 825 KB, or 287 KB with gzip. It has no imports. A page runs scripts that its users write, with the same step limit and memory cap.

  • A small ES module for the page, a Web Worker, and Node.js.
  • Stop in a worker. A long script runs off the main thread, and the page can end it.
  • Examples: a REPL, a rule engine with limits, a worker with Cancel, and a Node.js runner.
Try it in your browser Read the WebAssembly guide
app.js
import { Interp } from "./ztcl.mjs";

const tcl = await Interp.create("./ztcl.wasm", {
  stepLimit: 10_000,
  memLimit: 8 << 20,
});
tcl.eval("proc price {q u} {expr {$q * $u}}");
tcl.eval("price 3 4.5");
// { ok: true, result: "13.5", output: "" }
tcl.eval("while 1 {}");
// { ok: false, result: "step limit reached", output: "" }

Numeric scripts

SIMD point procs, about 15 ns for each point.

A point proc compiles one body to a vector program that runs over blocks of 1024 points. Your program gives it arrays of coordinates and gets arrays of results.

On the fuzzy skin benchmark over 10 million points, the vector path uses about 15 ns for each point. The normal path uses about 230 ns. The two paths give the same results, bit for bit.

Read about point procs

fuzzy.tcl
point proc fuzzy {x y z feature} {
    if {$feature ne "outer_wall"} { return }
    set n [noise3 $x $y [expr {$z * 4}]]
    offset [expr {$n * 0.3}]
}

Tested hard

37 413 passing tests of the Tcl suite.

The test suite of Tcl 8.6.16 is the measure of compatibility. ztcl follows the 12 rules of Tcl and the core commands of Tcl 8.6: lists, strings, dicts, arrays, expr, regexp, namespaces, try, apply, lmap, and TclOO.

  • The Tcl suite. 37 383 of 46 494 tests pass in all 152 files (80.4 %). The suite also runs with the JIT on for each proc.
  • Differential fuzzing. zig build jit-fuzz compares random programs in the interpreter and in the JIT, and fuzzes the assembler and the verifier.
  • A comparison tool. tools/jit-diff.sh compares the output, errors, and steps of the JIT and the interpreter on the test scripts.
  • Stress modes. --jit-stress forces the rare paths of the compiler, and --gc-stress N starts a collection at each Nth allocation.
  • W^X code memory. Code memory is never writable and executable at once.
  • A verifier. It checks each bytecode before the JIT compiles it.
  • No script values in code. No value from a script goes into the machine code.
  • A code scan. tools/jit-scan.sh searches the machine code for the constants of a script.

Compatibility has the result for each test file, and Tests and benchmarks has the commands.

Status

Experimental, and measured in the open.

ztcl aims to become a complete drop-in replacement for Tcl. It is not one yet. APIs and behavior can change in any release.

  • WorksTcl 8.6.16 test suite: 37 383 of 46 494 tests pass in all 152 files (80.4 %). Compatibility has the result for each file.
  • WorksThe interpreter, point procs, and the WebAssembly build.
  • ExperimentalThe JIT on x86-64 Linux. It is off by default. Turn it on with --jit and --jit-tier2.
  • In progressThe JIT on arm64 macOS.
  • WorksTclOO method calls have call caches. With --jit, bf_oo uses 0.37 of the instructions of tclsh 8.6.16, and 0.46 with the interpreter only.
  • Open bugA step limit cost bug (#6): a recheck after an epoch change costs O(n²) CPU time.
  • NoteThe code and the docs were written largely with AI coding agents, under human direction. Review the code before you depend on it.
