Speed and the JIT

A bytecode VM, and a JIT compiler for hot loops.

The interpreter compiles each script to bytecode. On x86-64 Linux, x86-64 Windows, arm64 Linux, and arm64 macOS, the JIT is on by default. It compiles hot procs to machine code, and tier 2 keeps integer and double loop variables in registers. --no-jit or ZTCL_JIT=off turns it off. tclsh 8.6 and 9 have no JIT.

Larger programs

Three programs of kostya/benchmarks: the brainfuck interpreter bf.tcl, its TclOO version bf_oo.tcl, and base64. With small.b, each output of ztcl equals the output of tclsh 8.6.16.

Exact, deterministic limits

Limits that Tcl does not have.

The interp limit command of Tcl counts commands and time, and it has no memory limit. ztcl counts compute units exactly and puts a hard cap on memory. Your program sets both before it runs a script that it did not write.

An exact compute limit

Each command and each loop pass uses compute units. At the limit, the script stops with an error that catch and try cannot catch.

  • The limit holds in JIT machine code too.
  • No clock is involved, so a slow machine gets the same count.

A hard memory cap

The heap of an interpreter and its children never goes above twice the memory limit. One command can go over the limit by at most the limit itself.

  • A large request stops before the allocation.
  • Nesting limits protect the native stack.

The same stop on each run

A script stops at the same point on each machine and in each JIT tier. A JIT run gives the same counts of compute units as the interpreter on the whole Tcl test suite.

  • With no capability on, output depends only on the script, the seed, and the inputs.
  • The collector can move the point of the memory error. --gc off makes it exact.

Host access is a capability

The safe interps of Tcl also remove files, sockets, and exec. In ztcl, the default interpreter starts with no host command, and your program turns on each capability with its own policy.

  • file and channels stay inside one root folder.
  • socket follows a network policy: loopback, an allowlist, or any.
  • A child interp never has more capabilities than its parent.
  • exec is not sandboxed. A process from exec runs outside the root folder and outside each limit, with the full power of the user.

Threads

Real threads, with limits for each one.

The commands of the Tcl Thread package: thread::*, tsv::*, tpool::*, mutexes, and conditions. Each thread has its own interpreter, heap, and JIT code, and no value crosses threads by pointer.

  • Limits for each thread and totals for the group: threads, compute units, memory, and queue length.
  • A thread that passes a limit stops alone. The other threads keep running.
  • In the browser too, with one Web Worker for each thread.

Built-in JSON

JSON faster than Node.js and Python.

ztcl::json is a Zig form of the simdjson algorithm. It finds the structure of 64 bytes at a time with vector instructions, and it makes Tcl dicts and lists.

  • Faster than each scripting runtime on twitter.json and citm_catalog.json. On the number-heavy canada.json, Python orjson and pysimdjson are faster.
  • ztcl::json get reads one value at a path with no full parse, at 798 to 2,489 MB/s.
  • The tcllib names json and json::write work over the same code.

Embedding in Zig

One static binary. No C toolchain.

ztcl is a Zig package with no dependency outside the Zig standard library. zig fetch adds it, and no C toolchain is necessary.

  • Cross-compiles with zig build -Dtarget=…. From x86-64 Linux, it builds for arm64 Linux, arm64 macOS, x86-64 Windows, and 64-bit RISC-V Linux. CI tests on Linux, macOS, and Windows.
  • register(name, fn) adds a native command.
  • output is the callback of puts.
  • disableJit() turns off the JIT. The JIT is on by default where the build and the system have one.

WebAssembly

The same interpreter in the browser.

npm install @beetlebug/ztcl gives the WebAssembly build with types. The module has no imports. A page runs scripts that its users write, with the same compute limit and memory cap.

  • A small ES module for the page, a Web Worker, and Node.js.
  • Stop in a worker. A long script runs off the main thread, and the page can end it.
  • Threads in Web Workers, on a cross-origin isolated page.
  • Procs compiled to WebAssembly. ztcl compile --wasm gives each proc a WebAssembly function with the same results and limits. An integer loop runs in 0.28 times the time of the interpreter.
  • Examples: a REPL, a rule engine with limits, a worker with Cancel, and a Node.js runner.

Numeric scripts

SIMD point procs, about 15 ns for each point.

A point proc compiles one body to a vector program that runs over blocks of 1024 points. Your program gives it arrays of coordinates and gets arrays of results.

On the fuzzy skin benchmark over 10 million points, the vector path uses about 15 ns for each point. The normal path uses about 230 ns. The two paths give the same results, bit for bit.

Read about point procs

fuzzy.tcl
point proc fuzzy {x y z feature} {
    if {$feature ne "outer_wall"} { return }
    set n [noise3 $x $y [expr {$z * 4}]]
    offset [expr {$n * 0.3}]
}

Tested hard

37,413 passing tests of the Tcl suite.

The test suite of Tcl 8.6.16 is the measure of compatibility. ztcl follows the 12 rules of Tcl and the core commands of Tcl 8.6: lists, strings, dicts, arrays, expr, regexp, namespaces, try, apply, lmap, and TclOO.

  • The Tcl suite. 37,413 of 46,494 tests pass in all 152 files (80.5 %). The suite also runs with the JIT on for each proc.
  • Differential fuzzing. zig build jit-fuzz compares random programs in the interpreter and in the JIT, and fuzzes the assembler and the verifier.
  • A comparison tool. tools/jit-diff.sh compares the output, errors, and compute units of the JIT and the interpreter on the test scripts.
  • Stress modes. --jit-stress forces the rare paths of the compiler, and --gc-stress N starts a collection at each Nth allocation.
  • W^X code memory. Code memory is never writable and executable at once.
  • A verifier. It checks each bytecode before the JIT compiles it.
  • No script values in code. No value from a script goes into the machine code.
  • A code scan. tools/jit-scan.sh searches the machine code for the constants of a script.

The language has the result for each command and the differences from Tcl.

Status

Experimental. APIs can change in any release, and ztcl is not yet a drop-in replacement for Tcl. The JIT is on by default. The code and the docs were written largely with AI coding agents, under human direction, so review the code before you depend on it. The issues and the milestones have the roadmap.
